WAYMARK – THIẾT KẾ BACKEND, API VÀ DATABASE
Tài liệu bàn giao kỹ thuật cho đội backend
Phiên bản
v1.0
Mục tiêu
Định nghĩa kiến trúc backend, API, dữ liệu lõi và chiến lược mở rộng nhiều user cho Waymark.
Waymark là ứng dụng lưu giữ và khám phá kỷ niệm gắn với địa điểm thật, lấy bản đồ làm bề mặt nội dung chính thay vì feed chữ truyền thống.
Đề xuất kiến trúc ưu tiên triển khai nhanh giai đoạn đầu bằng modular monolith tách module rõ ràng, kết hợp job queue và event-driven cho các tác vụ nặng. Khi tăng trưởng, từng module có thể tách thành service độc lập mà không phá vỡ hợp đồng API.
Tài liệu này giả định sản phẩm có mobile app iOS/Android, media lưu trên object storage, chat là tin nhắn 1-1 hoặc nhóm nhỏ, và phạm vi hiện tại chưa bao gồm live streaming.
[Chưa xác minh] 
Một số quyết định như retention của chat, yêu cầu pháp lý theo quốc gia, anti-spam policy và mức độ real-time của map chưa có trong brief nên đang được đề xuất theo thông lệ sản phẩm xã hội dựa trên vị trí.

1. Tóm tắt điều hành
[Tổng hợp] 
Yêu cầu sản phẩm nhấn mạnh 5 nguyên tắc: map first, memory first, nearby first, low friction và layered discovery. Vì vậy backend phải giải quyết tốt ba bài toán lõi: nội dung gắn với vị trí-thời gian, truy vấn nearby tốc độ cao và phân tầng riêng tư/quan hệ xã hội.
Phương án phù hợp nhất cho giai đoạn 0 → 1 triệu user đăng ký là:
• PostgreSQL + PostGIS làm source of truth cho user, memory, social graph, place, privacy và geospatial query.
• Redis cho cache, session, rate limit, feed candidates ngắn hạn và pub/sub nhẹ.
• Object storage + CDN cho ảnh/video; metadata của media nằm trong PostgreSQL.
• Message broker/job queue cho notification, media processing, resurfacing, analytics, chống spam và fan-out event.
• OpenSearch/Elasticsearch là tùy chọn phase 2 cho full-text caption, place search nâng cao và ranking chuyên sâu; chưa bắt buộc ở MVP.
2. Nguyên tắc kiến trúc
Nguyên tắc
Hàm ý kỹ thuật
Map-first domain model
Mọi memory bắt buộc có geolocation, place snapshot hoặc geohash; mọi truy vấn home phải ưu tiên theo không gian trước rồi mới tới social/trending.
Privacy-first read path
Cùng một vùng địa lý nhưng user chỉ thấy memory phù hợp với public, friends hoặc private theo quan hệ tại thời điểm đọc.
Write nhẹ, read tối ưu
Tạo memory phải ít bước; các tính toán nặng như clustering, reverse geocoding, media transcoding, trending score, resurfacing và notification đẩy sang async.
Single source of truth rõ ràng
Không cho phép dữ liệu vị trí nằm rải rác không chuẩn hóa; cần tách snapshot hiển thị khỏi place canonical để tránh thay đổi dữ liệu lịch sử.
Scale bằng tách nóng
Các phần có profile tải khác nhau như chat, media và notification phải có ranh giới module rõ để tách khỏi core app khi cần.
3. Kiến trúc backend đề xuất
3.1 Kiểu kiến trúc
[Sáng tạo mới] 
Khuyến nghị triển khai theo mô hình modular monolith + asynchronous workers trong 2 phase đầu. Toàn bộ API công khai đi qua một API Gateway/BFF, nhưng code backend chia theo domain module độc lập, mỗi module có service layer, repository layer, event contract và migration riêng.
Các module lõi:
• Identity & Auth
• User Profile & Social Graph
• Place & Geo Index
• Memories & Media
• Feed/Discovery
• Chat
• Engagement (like/comment/share/save/report/block)
• Notifications
• Collections/Drafts/Resurfacing
• Moderation & Trust/Safety
• Admin & Analytics Export
3.2 Sơ đồ logic
Lớp
Trách nhiệm
Mobile App
Map UI, camera, chat UI, profile, notification center
API Gateway / BFF
JWT verification, request shaping, versioning, rate limit, edge auth, aggregation response cho mobile

Auth, users, memories, places, social graph, comments, likes, collections, drafts
Realtime Service
WebSocket hoặc managed realtime channel cho chat, typing, online state, notification badge

Media processing, OCR/metadata extraction nếu cần, push notification, resurfacing, ranking materialization, geo-cluster cache
Data Layer
PostgreSQL/PostGIS, Redis, object storage, search index tùy chọn, broker/queue
[Sáng tạo mới] 
Nếu team muốn đi xa hơn về deploy độc lập, thứ tự tách service nên là: chat, notification, media pipeline, feed/discovery. Auth + user + memories + places vẫn nên ở cùng core service trong giai đoạn đầu để giảm distributed transaction.

5. Luồng nghiệp vụ chính
Luồng
Xử lý backend
Đăng ký/đăng nhập
Client gửi email/sđt hoặc social token -> Auth module xác minh -> tạo/ghép account -> issue access token + refresh token -> emit event user.created hoặc user.logged_in.
Mở map trang chủ
Client gửi lat/lng, zoom, filter, privacy scope -> Discovery service query nearby candidate memories theo bounding box hoặc radius -> áp dụng privacy + block + geo ranking -> trả cluster/pin preview.
Tạo memory
Client upload media qua signed URL -> gọi create memory với caption, mood, location, timestamp, privacy -> DB ghi memory + media + place snapshot -> queue xử lý thumbnail/transcode/reverse geocode/notification/trending.
Xem chi tiết memory
Fetch memory detail -> kiểm tra privacy -> trả media, caption, place snapshot, counts, replies, related memories cùng địa điểm.
Chat
Tin nhắn đi qua realtime gateway -> persist message -> fan-out tới participants -> cập nhật conversation unread count.
Resurfacing
Worker chạy batch theo lịch -> tìm memory đủ điều kiện 1 năm trước hoặc revisit place -> tạo notification/resurfacing card materialized cho user.

8. Chỉ mục, phân vùng và scale
Index / Partition
Mục đích
memories(location)
GIST trên geography(Point,4326) để truy vấn nearby ST_DWithin.
memories(geohash, posted_at desc)
Tối ưu cache/scan theo tile hoặc geohash prefix.
memories(user_id, posted_at desc)
Trang cá nhân, timeline user.
memories(place_id, posted_at desc)
Xem các memory cùng địa điểm.
likes(memory_id)
Đếm like, kiểm tra user đã like.
comments(memory_id, created_at asc)
Load comment tree theo thời gian.
user_relationships(source_user_id, status)
Danh sách following/friends.
user_relationships(target_user_id, status)
Followers và mutual lookup.
messages(conversation_id, sent_at desc)
Phân trang tin nhắn.
notifications(user_id, is_read, created_at desc)
Notification center.
[Sáng tạo mới] 
Chiến lược scale khuyến nghị:
• Partition bảng memories theo posted_at hàng tháng hoặc hàng quý khi volume cao, nhưng vẫn giữ index geospatial cục bộ trên partition.
• Partition messages theo conversation shard hoặc sent_at khi chat tăng mạnh.
• Counter như likes_count, comments_count không cập nhật bằng COUNT(*) realtime; dùng bảng counter hoặc event consumer để materialize.
• Map home không query trực tiếp toàn bán kính ở khu vực siêu đông; dùng tile cache/cluster cache theo zoom level trong Redis.
• Dùng read replica cho profile/timeline/detail read-heavy; write vẫn vào primary.
• Định nghĩa rank score materialized: freshness + distance + social affinity + engagement velocity, cập nhật async thay vì tính lại toàn phần cho mỗi request.
8.1 Công thức dữ liệu nearby
[Sáng tạo mới] 
Một truy vấn nearby thực tế nên gồm 4 tầng lọc:
• Tầng 1: lọc không gian bằng bbox hoặc radius với PostGIS.
• Tầng 2: lọc quyền riêng tư và block.
• Tầng 3: lọc business rules như status active, media processed, không bị report quá ngưỡng.
• Tầng 4: xếp hạng theo score = w1*freshness + w2*distance_decay + w3*social_affinity + w4*engagement_velocity.
9. Bảo mật, riêng tư và moderation
Mảng
Khuyến nghị
Authentication
Access token ngắn hạn + refresh token xoay vòng; device binding nếu cần.
Authorization
Mọi read memory phải qua policy check: owner/self, friend graph, block graph, visibility status.
Privacy snapshot
Khi tạo memory, lưu place snapshot riêng để lịch sử không bị thay đổi khi place canonical đổi tên.
Rate limiting
Giới hạn OTP, login, create memory, comment, chat send, report.
Media safety
Scan virus/nội dung độc hại; tách media processing sandbox.
Abuse prevention
Report, mute, block, shadow limit cho spam account, device fingerprint tùy pháp lý.
Data retention
Có soft delete + purge policy cho memory, chat, notification, logs.
Auditability
Lưu audit cho thay đổi quyền riêng tư, xóa nội dung, hành động admin.

Phụ lục A – Quy ước dữ liệu quan trọng
• [Sáng tạo mới] privacy_level đề xuất: 1=private, 2=friends, 3=public.
• [Sáng tạo mới] relation_type đề xuất: 1=follow, 2=friend_request, 3=friend, 4=block, 5=mute.
• [Sáng tạo mới] memory status đề xuất: draft, published, hidden, deleted, archived, under_review.
• [Sáng tạo mới] mood_code lưu dạng enum mềm hoặc bảng cấu hình để app có thể thêm preset mà không cần migration lớn.
• [Chưa xác minh] Nếu sản phẩm muốn “bạn từng ở đây” thật chính xác, cần định nghĩa ngưỡng revisit theo bán kính 30–100m và thời gian dwell tối thiểu.
